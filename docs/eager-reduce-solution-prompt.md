I need a rigorous solution design for a concrete interoperability problem

The attached report, `docs/eager-reduce-conversion-report.md`, contains the

## Context

The project uses Rocq as an independent checker for Lean libraries:

```text

             -> rocq-lean-import -> Rocq kernel
```

The target is cslib, but the solution must be generic. We must not manually
rewrite or reprove cslib theorems in Rocq, match declaration names, add axioms,
or trust an answer computed only by the importer. The resulting declarations
must remain efficiently recheckable by Rocq and replayable from `.vo` files.

## Exact blocker

The current declaration is:

```text
Std.DTreeMap.Internal.Impl.link2._unary._proof_1
```

It is generated by the termination proof of
`Std.Data.DTreeMap.Internal.Impl.link2`. The minimal Lean source is:

```lean
import Std.Data.DTreeMap.Internal.Operations
#check Std.DTreeMap.Internal.Impl.link2
```

Lean accepts a reflexivity proof argument wrapped in:

```lean
@[expose] def eagerReduce {α : Sort u} (a : α) : α := a
```

Although this is definitionally the identity, the Lean kernel recognizes the
wrapper at an application call site and sets a scoped `m_eager_reduce` flag
while comparing the argument's inferred type with the expected domain. Among
other things, this permits its Boolean-reflection path even when the Boolean
term contains free variables:

```cpp
if ((!has_fvar(t) || m_eager_reduce) && is_constant(s, Bool.true)) {
    if (is_constant(whnf(t), Bool.true)) return true;
}
```

After translation, Rocq has only an ordinary transparent identity definition;
it does not receive the local operational effect of Lean's marker. It must
compare a type schematically like:

```text
true = true
```

with:

```text
largeOpenBooleanComputation = true
```

Stock Rocq conversion appears logically capable of the reduction, but the
isolated check stalls and consumes several GB.

An importer-side evaluator reduces the Boolean to `true` in about three
seconds. One trace has 556 steps: 197 applications of small generic equations,
334 ordinary definitional reductions, and 25 reflected arithmetic/Boolean
steps. Therefore computation is not the main obstacle. The obstacle is
producing compact evidence that Rocq can check without flattening a highly
shared term.

A representative endpoint has only 329 physically unique nodes but 17,687
nodes as a tree. Flat equality composition and opaque checkpointing repeat
large endpoints. Moreover, paths pass through dependent projection
scrutinees, so replacing the scrutinee may change the projection's type; a
homogeneous one-hole context and `f_equal` are not generally valid.

Experiments with flat proof traces, opaque chunks, let-based sharing, VM/native
casts, modified conversion heuristics, HEq transports, and hierarchical
zippers have not yielded a verified solution. The huge WIP branch
`fix/eager-reduce-proof-producing` is an experiment, not a proposed patch.
